# راهنمای اجرای واقعی و اتصال به WordPress

## معماری فعلی به زبان ساده

- **Cloudflare Worker** بک‌اند برنامه است: APIها، ورود Owner/Team، دسترسی مشتری و منطق پروژه را اجرا می‌کند.
- **D1** دیتابیس برنامه است: درخواست‌ها، پروژه‌ها، اعضای تیم، نقش‌ها و اعداد Finance را نگه می‌دارد.
- **R2** فایل‌های خصوصی پروژه مثل عکس‌ها و PDFها را نگه می‌دارد.
- **GitHub** فقط محل نگهداری نسخه کد، بررسی تغییرات و اجرای تست‌هاست؛ دیتابیس و سیستم ورود واقعی را اجرا نمی‌کند. GitHub Pages برای این پرتال خصوصی مناسب نیست.
- **Supabase** یک بک‌اند جایگزین است، نه مقصد مستقیم این ZIP. انتقال به Supabase یعنی بازنویسی D1 به PostgreSQL، ساخت RLS، انتقال R2 به Storage و عوض‌کردن آداپتورهای سرور. برای اجرای فعلی لازم نیست.

## روش پیشنهادی برای WordPress

WordPress را برای سایت اصلی و صفحات مارکتینگ روی `alertconstruction.com.au` نگه دارید و پرتال را روی یک ساب‌دامین مثل `app.alertconstruction.com.au` یا `portal.alertconstruction.com.au` اجرا کنید. دکمه‌های Customer Sign In، Team Sign In و Request a Job در WordPress به این ساب‌دامین لینک می‌شوند. ظاهر دو بخش یکسان می‌ماند، اما پرتال بک‌اند امن خودش را حفظ می‌کند.

این ZIP را نمی‌توان مستقیم در بخش Theme یا Plugin وردپرس آپلود کرد، چون وردپرس PHP/MySQL اجرا می‌کند و کد فعلی TypeScript/Worker/D1/R2 است. انتقال صددرصد داخل وردپرس یک پروژه جدا برای ساخت افزونه PHP، جدول‌های MySQL، WordPress REST API، نقش‌ها و مجوزها و فایل‌های خصوصی است.

## کاری که الان انجام دهید

1. ZIP نهایی را Extract کنید و محتویات پوشه اصلی آن را در یک repository خصوصی GitHub قرار دهید. فایل `.env`، پسورد، Team Code، دیتابیس و اطلاعات مشتری را هرگز commit نکنید.
2. روی کامپیوتر Node.js 22.13 یا جدیدتر نصب کنید و داخل پوشه پروژه اجرا کنید:

   ```bash
   npm ci
   npm test
   npm run lint
   ```

3. برای تست محلی UI دستور `npm run dev` را اجرا کنید. این حالت برای بررسی ظاهر است؛ D1/R2 واقعی در محیط Cloudflare/Sites اجرا می‌شوند.
4. در Secret Manager محیط میزبانی، مقادیر فایل `release-docs/ENVIRONMENT-TEMPLATE.txt` را تنظیم کنید. مقادیر امن را با `node scripts/security-setup.mjs` بسازید. پسورد Owner را داخل GitHub نگذارید.
5. binding دیتابیس را دقیقاً با نام `DB` و bucket خصوصی R2 را دقیقاً با نام `BUCKET` وصل کنید.
6. نسخه را deploy کنید و ابتدا با اطلاعات تست غیرواقعی این مسیرها را بررسی کنید: ارسال درخواست، دریافت کد، ورود با کد، ورود با همان Email، ورود با همان Phone، Owner login، Team request، Owner approval، تغییر role، Finance و upload/download.
7. بعد از موفقیت تست‌ها، یک پروژه واقعی کم‌ریسک وارد کنید و نتیجه را در Customer و Owner بررسی کنید. قبل از استفاده گسترده، backup، مانیتورینگ و سیاست حریم خصوصی را فعال کنید.
8. دامنه/ساب‌دامین را تهیه کنید. در پنل DNS، ساب‌دامین انتخابی را طبق دستور دقیق سرویس میزبان به deployment پرتال متصل کنید؛ مقدار CNAME/record به میزبان نهایی شما بستگی دارد.
9. در WordPress، لینک منوها و دکمه‌های ورود را به ساب‌دامین پرتال تغییر دهید. برای پرتال authenticated از iframe استفاده نکنید.
10. وقتی این معماری چند بار با پروژه واقعی تست شد، سایت WordPress را روی دامنه اصلی و پرتال را روی ساب‌دامین live کنید.

## اگر حتماً همه‌چیز باید داخل WordPress باشد

در آن صورت باید یک WordPress Plugin کامل ساخته شود: schema در MySQL، endpointهای REST، نقش‌ها و capabilityها، session/auth، فرم درخواست، customer lookup، داشبوردها و مدیریت فایل خصوصی. این «انتقال فایل» نیست؛ بازنویسی بک‌اند است. پیشنهاد عملی و کم‌ریسک فعلی همان WordPress + پرتال روی ساب‌دامین است.

## سرویس ایمیل اختیاری

ورود مشتری هیچ ایمیل یا SMS نمی‌فرستد و به Resend یا Twilio نیاز ندارد. فقط اگر می‌خواهید هنگام درخواست عضو جدید تیم علاوه بر اعلان داخل داشبورد، ایمیل هم برای Owner ارسال شود، `RESEND_API_KEY` و `TEAM_NOTIFICATION_EMAIL_FROM` را تنظیم کنید.
